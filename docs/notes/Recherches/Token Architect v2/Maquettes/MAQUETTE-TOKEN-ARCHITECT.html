UCM Token Architect

Ces maquettes dessinent les fonctions du plan d'implémentation. Chaque fenêtre part des écrans réels de l'explorateur et de Nomenclature, figés depuis leurs galeries sombres. Les éléments nouveaux emploient les classes de ces deux plugins et la feuille architect.css. Une pastille rose numérotée marque chaque changement. La légende de même numéro, sous la fenêtre, dit ce qu’il montre. Cette version applique les retours du mainteneur du 22 octobre. Un encadré bleu « Réponse » répond à chaque question, sous la fenêtre qu'elle concerne. La section 10 reprend les retours un par un.

1 · Le langage visuel commun

Chaque plugin signale aujourd'hui ses données, ses changements et ses constats avec ses propres formes. Palettes range ses constats en bloquant, alerte, notice et promesse. L'exporteur a une pastille danger. Nomenclature a six pastilles d'état, des jetons et une ligne de réussite. L'explorateur écrit ses chemins en gris. Le socle ne partage que les rôles de couleur, les boutons, les onglets et la feuille.

La proposition : un seul langage visuel pour tous les plugins. Le kit en porte le vocabulaire. Le socle en porte les styles et les composants. Un plugin n'en redéfinit aucun. Token Architect l'emploie le premier.

Deux règles le tiennent sobre. Un chemin reste gris tant que l'écran n'a rien à en montrer. Une couleur dit toujours la même chose, d'un plugin à l'autre.

2 · Le parcours

Le plugin s'ouvre dans le mode qui correspond au fichier. Un fichier de tokens ouvre le mode Tokens. Une sélection de composant ouvre le mode Composant. La bascule de la barre change de mode. Les deux modes ont les mêmes onglets : Corrections, Questions et À faire dans Figma. Le mode Tokens y ajoute Règles.

Mode Tokens

Dans le fichier des tokens

  1. L'arbre et la table montrent les variables, dans les modes choisis.
  2. Corrections applique les noms sûrs, les portées et les modes.
  3. Questions demande les choix.
  4. À faire dans Figma liste ce que le plugin n'écrit pas.
  5. Règles montre l'écriture et le vocabulaire.
  6. Un clic sur une variable ouvre sa fiche.
  7. Des variables préparées ou une règle reçue attendent en tête de la barre.

Mode Composant

Dans le fichier des composants

  1. Le designer sélectionne un composant. La vue Composant le montre.
  2. Analyser lit tous ses variants.
  3. Le bouton Analyse ouvre le panneau. Sa pastille compte les constats.
  4. Corrections applique les liaisons sûres.
  5. Questions demande les choix.
  6. À faire dans Figma liste le reste.
  7. Un clic sur un constat sélectionne le calque dans Figma.
  8. Ctrl+Z défait une correction. Actualiser relit le composant.

Préparation des tokens

Entre les deux fichiers

  1. Composant sans tokens : Préparer les tokens.
  2. Répondre aux questions, puis Préparer.
  3. Fichier des tokens : les variables préparées attendent. Créer.
  4. Publier la bibliothèque.
  5. Fichier des composants : Actualiser. Corrections propose les liaisons.
  6. L'Historique annule une création.

4 · Mode Tokens

La fenêtre passe à 1360 × 800. L'arbre et la table restent à gauche. La barre latérale de 640 px, la largeur de Nomenclature, l'affiche. L'inspecteur devient une feuille, comme la fiche d'un terme. Le fichier d'exemple est en cours de passage à UCM : sa collection Interface deviendra components.

4a · Corrections, filtrées par l'arbre

Tokens · Corrections
  1. La barre du haut porte le nom UCM Token Architect et le bouton Configuration.
  2. Les onglets de l'explorateur disparaissent. La table montre les variables.
  3. Les modes affichés tiennent sur une ligne. Chaque menu nomme sa collection.
  4. La table montre toujours les renommages cochés. Le nom reste entier. Seul le terme nouveau est vert.
  5. Un clic sur un terme vert ouvre sa carte dans Corrections.
  6. La collection choisie dans l'arbre filtre la barre latérale. Une puce le montre. Sa croix enlève le filtre.
  7. Le pied dit ce qu'Appliquer renomme.
  8. Le bouton à droite de Collections replie toutes les sections de l'arbre, sauf celle qui est choisie.
  9. À 640 px, Nomenclature garde ses deux colonnes Aujourd'hui et Après l'application, comme au tour 3.

4b · Questions, et un terme filtré depuis Règles

Tokens · Questions
  1. Ouvrir une question ne change pas la table.
  2. « Voir les 2 variables » filtre la table, comme une recherche.
  3. Dans chaque nom, le terme de la question est en rose. C'est un groupe.

Réponse

« Je ne vois pas le lien entre le tableau de tokens et les questions. »

La version précédente n'en avait pas. La table montrait d'autres variables que la question, et le fond de deux lignes changeait seul.

Le lien est maintenant un geste du designer. Chaque question porte « Voir les N variables ». Ce lien pose un filtre dans le champ de recherche de l'arbre, comme une recherche tapée. La table ne garde que ces variables. Le terme en cause y est en rose, la couleur d'un groupe mis en avant. Aucune cellule ne change de fond.

Tokens · Terme filtré depuis Règles
  1. Un clic sur un terme ouvre sa fiche. La table ne change pas.
  2. « Filtrer la table sur ce terme » pose le filtre.
  3. Le filtre s'affiche dans la recherche de l'arbre. La croix l'enlève.
  4. La table montre les variables qui emploient le terme ou une de ses variantes.

Réponse

« Une action de filtrage explicite, matérialisée comme une recherche dans l'input principal. Non ? »

Oui. Ouvrir la fiche d'un terme ne filtre plus rien. La fiche porte le bouton « Filtrer la table sur ce terme ». Le filtre se pose dans le champ de recherche de l'arbre, sous forme de puce. La croix l'enlève, comme une recherche qu'on efface.

Le même geste sert partout : « Voir les N variables » sur une question, « Afficher ces N variables dans la table » sur la fiche d'une variable.

La table montre maintenant les variables du terme. Celles qui emploient déjà background ont le terme en rose. Celles que Corrections renomme ont le terme nouveau en vert.

4c · À faire dans Figma, et les portées dans Corrections

Réponse

« Je ne comprends pas pourquoi ça s'appelle Structure. Il faudrait peut-être repenser le nom de tous les onglets ? »

Structure rangeait ensemble des constats qui se règlent de trois façons. Le plugin en corrige certains. D'autres demandent un choix. Les derniers se règlent dans Figma.

Proposition : les deux modes prennent les mêmes onglets, nommés d'après ce que le designer fait.

  • Corrections : ce qu'Appliquer écrit. En mode Tokens, les renommages, les portées et les modes.
  • Questions : ce que le designer tranche.
  • À faire dans Figma : ce que le plugin ne peut pas écrire.
  • Règles, en mode Tokens seulement : l'écriture et le vocabulaire qui produisent les corrections.

L'onglet Structure disparaît. Ses constats se rangent dans les trois premiers. Le contenu des cartes de Nomenclature ne change pas, seul le nom Renommages devient Corrections. Question M-12.

Tokens · À faire dans Figma
  1. L'onglet reprend les diagnostics de l'explorateur et les règles du profil UCM que le plugin ne corrige pas.
  2. Les constats se rangent par sujet : alias, modes, valeurs, couches.
  3. Chaque carte porte le type de son alerte : liseré, icône, mot.
  4. Une carte ouverte ne répète pas sa tête. Elle donne des faits nouveaux et « Ouvrir la fiche ».
  5. Un token de composant qui vise utility part dans Questions : plusieurs tokens du thème conviennent.

Réponse

« Comment deux variables pourraient se viser l'une l'autre ? Figma interdit ce genre d'affectation. Et la ligne du dessous répète la ligne du dessus. »

Elles ne le peuvent pas. Figma refuse un alias qui ferme une boucle. Le constat est retiré. L'exemple est remplacé par un alias rompu : une variable qui vise une variable supprimée.

Une carte ouverte ne redit plus le chemin de sa tête. Elle donne la cible perdue, ce que visent les voisines, et le lien vers la fiche.

Tokens · Corrections, modes et portées
  1. Les corrections de modes et de portées suivent les renommages, dans le même onglet.
  2. La tête dit l'effet de la correction, en mots de designer.
  3. La colonne Après l'application dit où Figma proposera la variable.
  4. Appliquer range la correction dans l'Historique.

Réponse

« On ne comprend rien à : Figma propose ces 3 variables pour tous les champs. Elles servent seulement aux fonds. »

Une portée (scopes dans l'API Figma) décide dans quels sélecteurs Figma propose une variable. Une variable réglée sur « tous les champs » apparaît partout : dans la couleur d'un texte, d'un contour, d'un fond.

theme/primary/surface/default est un fond teinté. La table du thème la réserve aux fonds. Avec les portées « fond de cadre » et « fond de forme », Figma ne la propose plus pour un texte ou un contour. Le designer ne peut plus la poser là par erreur.

La carte dit maintenant l'effet : « Proposer les fonds teintés seulement pour les fonds ». Sa ligne grise dit l'état actuel. La colonne Après l'application nomme les sélecteurs où la variable restera.

4d · La fiche d'une variable

Tokens · Fiche d'une variable
  1. Un clic sur un nom de la table ouvre la fiche. La ligne prend le fond de sélection de l'explorateur, sur toute sa largeur.
  2. La fiche reprend la feuille d'un terme de Nomenclature, avec une marge à gauche et à droite.
  3. Le titre ne met en avant que la variable, en olive. Ses groupes restent gris.
  4. La chaîne d'alias se dessine comme dans la vue Composant. Chaque nœud nomme sa collection et son mode. La valeur est au bout.
  5. « Comparer avec » est retiré.
  6. « Renommage à appliquer » montre le nom que Corrections propose.
  7. « Utilisée par » remplace l'onglet Dépendants. Son lien filtre la table.

Réponse

« Renommages de cette variable · 1 : c'est quoi ? Les renommages qui n'ont pas encore été appliqués ? »

Oui. Corrections propose un renommage pour cette variable, pas encore appliqué. Ici, la règle bg → background donnera Card/background/default.

La section s'appelle maintenant « Renommage à appliquer ». Elle n'apparaît que si un renommage attend. Son lien ouvre la carte de la règle dans Corrections.

Réponse

« C'est quoi “Marquer dans la table” ? »

Ce lien colorait dans la table les 3 variables qui visent celle-ci. Il s'appelle maintenant « Afficher ces 3 variables dans la table ». Il pose un filtre dans la recherche de l'arbre, comme les autres filtres.

4e · Bibliothèque, règle reçue, fichier hors UCM

Tokens · Bibliothèque lue depuis le fichier des composants
  1. Les noms s'affichent tout de suite.
  2. Une valeur pas encore lue montre un trait gris dans sa cellule, sans phrase.
  3. Corrections, Questions et À faire dans Figma sont grisés. Règles reste ouvert.
  4. L'alerte d'information nomme le fichier où renommer, avec son lien.

Réponse

« “Les valeurs de ce groupe se chargent. 8 variables sur 11.” Phrase incompréhensible. Est-elle vraiment utile ? »

Non. Dans un fichier de composants, Figma donne vite les noms des variables d'une bibliothèque. Chaque valeur demande un import, plus lent. Le plugin lit donc les valeurs du groupe ouvert, au fil de l'eau.

La phrase est retirée. Une valeur pas encore lue montre un trait gris dans sa cellule.

Réponse

« Est-ce qu'on peut mettre le lien vers le bon fichier dans l'alerte ? »

Oui, sous une condition. Figma ne donne pas à un plugin l'adresse du fichier d'une bibliothèque. La clé du fichier ouvert, figma.fileKey, n'est servie qu'aux plugins privés d'une organisation qui déclarent enablePrivatePluginApi. Nos manifestes ne le déclarent pas. figma.openExternal ouvre ensuite le lien.

  • Si les plugins UCM sont privés à l'organisation : on ajoute la déclaration. Token Architect retient sur le poste la clé du fichier des tokens la première fois qu'il s'y ouvre. Le lien marche ensuite.
  • Sinon : la Configuration demande une fois l'adresse du fichier des tokens. C'est un geste de plus pour le designer. Je ne le retiens pas sans ton accord.

Tant que le plugin ne connaît pas l'adresse, l'alerte nomme le fichier sans lien. Question M-13.

Tokens · Règle reçue du mode Composant
  1. Une règle préparée depuis un composant attend en tête de la barre.
  2. « Ajouter la règle » l'ajoute aux Règles. Corrections propose ensuite les noms.
Tokens · Fichier hors UCM
  1. L'arbre, la table et les fiches restent.
  2. L'alerte dit que le fichier n'est pas déclaré UCM.
  3. Son bouton ouvre la Configuration (question M-10).

Réponse

« La structure de l'alerte semble cassée. Et ça fait quoi si on clique sur “Déclarer l'architecture UCM” ? »

Elle était cassée. Nomenclature a sa propre classe bandeau, qui posait le texte en deux colonnes. L'alerte commune a maintenant sa classe à elle.

Le bouton s'appelle « Déclarer dans la Configuration ». Il ouvre Configuration › Réglages, à la section Architecture du fichier. Il n'écrit rien. Le designer y coche « Ce fichier suit l'architecture UCM ».

La coche range la déclaration dans le fichier. Token Architect contrôle alors les variables et ouvre ses onglets. UCM Palettes n'écrit plus dans theme, brands ni utility. Décocher rend l'état d'avant.

Tokens · Bibliothèque, texte de l'alerte

Réponse

« Le texte de l'alerte est absolument incompréhensible. Plus simple, plus direct. »

Nouveau texte : « Ces variables viennent de la bibliothèque Intencial Tokens. Pour les renommer, ouvrez ce fichier. » Puis le lien « Ouvrir Intencial Tokens ».

5 · Mode Composant

La fenêtre s'ouvre à 500 × 760 sur la vue Composant seule. Le bouton Analyse ouvre le panneau d'analyse : la fenêtre passe à 1040 × 760. La frontière entre la vue et le panneau se tire à la souris. Le composant d'exemple est Alert, avec 11 variants : 4 statuts × 3 styles, sans warning · filled.

5a · Avant la première analyse

Composant · Pas encore analysé
  1. La sélection d'un composant ne lance rien.
  2. Le bouton principal de la barre dit Analyser. Après la première analyse, il dit Actualiser.
  3. La phrase dit ce que l'analyse lit.
  4. Le panneau est ouvert ici. Il est fermé par défaut (5g).

5b · Corrections, et la section Variants

Composant · Corrections
  1. L'aperçu du composant reste en haut de la vue. C'est le repère visuel.
  2. La section Variants le suit. Elle a un titre, un cadre et un pied.
  3. Chaque case montre le constat le plus grave du variant : son icône, sa couleur et leur nombre.
  4. La vue montre toujours les liaisons que les corrections cochées changent. Seul le segment nouveau est vert. Un clic dessus ouvre sa carte.
  5. Les autres liaisons restent grises.
  6. La frontière entre la vue et le panneau se tire à la souris.
  7. L'onglet reprend le tour 3 de Renommages : cartes cochées, la règle en jetons ou en phrase, les deux colonnes Aujourd'hui et Après l'application, le pied Appliquer.
  8. La création des règles d'usage est une correction comme les autres. Ctrl+Z la défait.
Composant · Button, 216 variants, panneau fermé
  1. Au-delà de deux propriétés ou de 24 variants, la section passe par propriété.
  2. Une ligne par propriété, une puce par valeur.
  3. Chaque puce montre le constat le plus grave des variants qui ont cette valeur.
  4. Une puce choisie par ligne compose le variant affiché.
  5. Le menu de la section croise deux propriétés en tableau. Les autres restent fixées par leurs puces.

Réponse

« Comment ça se passe pour de très très gros composants avec plein de variantes ? »

Le tableau croise deux propriétés. Button en a quatre : 3 styles × 6 palettes × 4 états × 3 tailles font 216 variants. Aucun tableau lisible ne les tient dans 400 px.

La section passe donc par propriété dès qu'un composant a plus de deux propriétés ou plus de 24 variants. Sa longueur suit la somme des valeurs, pas leur produit. Button tient en 16 puces.

Une puce porte le constat le plus grave des variants qui ont sa valeur. Le designer voit vite que les problèmes se concentrent sur hover ou sur danger. Il choisit ces puces, et la vue montre le variant qu'elles composent. Question M-14.

5c · Un constat cliqué

Composant · Constat cliqué
  1. Un clic sur l'en-tête sélectionne le calque dans Figma et ouvre la carte.
  2. Un constat groupé sélectionne tous ses calques.
  3. L'aperçu de gauche entoure le calque et passe sur son variant.
  4. La carte ouverte donne les faits lus : champ, règle.
  5. « Ne plus proposer pour ces 2 calques » range ce choix dans le fichier. Toute l'équipe le voit.

Réponse

« J'ai pas compris ce que fait “Ignorer”. »

Ignorer voulait dire : cette liaison est voulue, ne la propose plus. Le plugin range ce choix sur le composant, dans le fichier. Toute l'équipe le voit. Actualiser ne repropose pas la correction.

Le choix se retrouve en bas de À faire dans Figma, sous « Ignorés », avec « Ne plus ignorer ». Le lien s'appelle maintenant « Ne plus proposer pour ces 2 calques ».

5d · Copier les liaisons d'un variant juste

Composant · Liaisons copiées depuis un variant
  1. Le designer choisit dans Variants un variant qu'il a lié à la main.
  2. Le pied de la section dit ce que fait le bouton.
  3. Corrections reçoit une carte. Sa première ligne dit la règle, sur un exemple.
  4. Seules les liaisons exactes sont cochées. Les cas à deux candidats partent dans Questions.

Réponse

« Fonctionnalité intéressante mais on ne comprend pas du tout l'action et ce qu'il va se passer si on clique dessus. »

Le designer a lié un variant à la main, ici info · standard. Le plugin lit ses liaisons : le calque icon vise colors/info/standard/icon.

Pour chaque autre variant, il cherche le calque de même nom. Il lui propose le token où seules les valeurs du variant changent : colors/error/outlined/icon pour error · outlined.

  • Ce token existe : la liaison est cochée.
  • Deux tokens conviennent : la liaison part dans Questions.
  • Aucun token n'existe : rien n'est proposé. Le constat reste dans À faire dans Figma.

Le clic ne lie rien. Il remplit Corrections. Appliquer écrit. Le bouton s'appelle « Copier ses liaisons aux autres variants ».

5e · Questions

Composant · Questions
  1. Les cartes reprennent le tour 3 de Questions : la question est la proposition, un seul bouton bordé, les autres réponses en texte.
  2. Dans le titre, le chemin reste gris. Le calque title et la variable title sont en olive.
  3. Dans la ligne du dessous, la liaison proposée garde le vert : c'est un ajout.
  4. La proposition est le candidat le mieux rangé par la structure de son nom. Rien n'est écrit avant la réponse.
  5. Renommer une valeur prévient que les développeurs devront modifier leur code.
  6. Un contour sans token renvoie à la préparation des tokens.
Composant · Question répondue
  1. La ligne verte dit le résultat de la réponse, puis l'étape suivante.
  2. Le compte de Corrections passe de 4 à 5.
  3. Rien n'est écrit avant Appliquer.

Réponse

« On ne comprend pas le message et ce qu'on est censé faire. »

Répondre « Lier » n'écrit rien. La liaison rejoint les autres dans Corrections, cochée. Appliquer l'écrit avec elles.

L'ancien message le disait avec les mots du plugin. La ligne verte dit maintenant le résultat et l'étape suivante : « title sera lié à colors/info/standard/title. Appliquez-le dans l'onglet Corrections. »

5f · À faire dans Figma

Composant · À faire dans Figma
  1. L'onglet liste ce que le plugin ne corrige pas. Chaque constat dit où le régler.
  2. Le type d'un constat se lit d'un coup d'œil : liseré, icône, mot, couleur.
  3. Le même code marque les cases de Variants et la pastille du bouton Analyse.
  4. Les intertitres reprennent les familles de l'exporteur, plus Tokens, Contraste et Typographie.
  5. Un message de l'exporteur garde son texte, précédé de « Message de l'exporteur ».
  6. Les constats ignorés passent en bas, grisés, avec « Ne plus ignorer ».

Réponse

« Repenser totalement le langage visuel de ce genre d'alerte, commun à tous les plugins. Savoir en un coup d'œil de quel type il s'agit. Le retrouver dans la matrice des variantes. »

La revue UX avait retiré la couleur des gravités. Elles redeviennent une échelle de cinq types : Bloquant, À corriger, À vérifier, Information, Tenu. Chaque type a sa couleur, son icône et son mot. Une couleur seule ne porte jamais le sens : l'icône change de forme à chaque type.

La même forme sert aux alertes en tête de liste, aux cartes de constat, aux cases de Variants et à la pastille du bouton Analyse. La planche de la section 1 la montre. Elle entre dans le socle pour tous les plugins (L-1).

6 · Contraste et accessibilité

Les contrôles d'état demandent un composant interactif. Ils sont montrés sur Button, qui a les propriétés Style, Palette, State et Size. La galerie n'a pas d'état de Button : seule la barre latérale est dessinée.

Alert · Contraste
  1. Chaque mesure montre la paire, le rapport et le seuil.
  2. Une ligne par marque et par thème.
  3. Un fond en dégradé dit que la mesure n'a pas pu se faire.
Button · Accessibilité
  1. Contour et anneau sont mesurés à 3:1.
  2. Les variants désactivés ne sont pas mesurés. Une ligne le dit.
  3. La zone cliquable se compare à 24 px, puis à 44 px en recommandation.
  4. Un texte sous 12 px reçoit une recommandation.
  5. Une ligne rappelle que la mesure porte sur le dessin Figma.
Button · Questions d'état
  1. Un survol lié au token du repos devient une question, sans réponse cochée.
  2. La question montre le token de survol qui existe, et ce que font les autres variants hover.
  3. « C'est voulu » range le choix dans le fichier.

Réponse

« On est sûr qu'il n'y aura pas de faux positifs ? Comment être sûr que la recommandation est pertinente ? »

On ne peut pas en être sûr. Un survol peut garder le fond du repos exprès, par exemple un bouton texte qui ne fait que souligner son libellé.

La règle trouve bien un seul candidat : le variant State=hover est lié à …/default/background, et …/hover/background existe. L'intention du designer reste inconnue. Selon la règle « aucune supposition », ces cas passent donc en Questions, sans réponse cochée.

La question donne un indice mesuré : combien des autres variants hover du composant emploient déjà un token de survol. « C'est voulu » range le choix dans le fichier, et la question ne revient plus. Question M-15.

7 · Préparation des tokens

Le parcours de l'aperçu de génération, sur Tag. Ses couleurs n'ont pas de token. Le parcours passe du fichier des composants au fichier des tokens, puis revient. Le mot « plan » disparaît de l'interface : le designer prépare des variables, puis les crée.

Réponse

« C'est vraiment possible de proposer une solution comme ça qui va fonctionner pour n'importe quel composant ? Ça paraît impossible. »

Non, pas pour n'importe quel composant. La préparation marche quand Figma donne des faits clairs :

  • des propriétés de variant que les registres UCM connaissent : palette, style, état, taille ;
  • des calques dont le rôle se lit : un texte, une icône dans une instance, le fond du variant, un contour.

Tag, Badge, Alert, Button et Chip en font partie. Chaque fait inconnu devient une question : une valeur Severity=Brand, un calque Frame 12, une propriété Density.

Un composant fait d'illustrations, de dégradés ou de plusieurs composants imbriqués reste hors de portée. Au-delà de 8 questions, préparer coûte plus que créer à la main. Dans ces deux cas, le résumé n'offre pas « Préparer les tokens » et dit pourquoi.

Réponse

« Motiver les choix proposés en fonction des usages attribués aux crans des palettes d'UCM Palettes, montrer sur quels tokens ça va pointer exactement, tout en gardant une interface simple. »

Chaque choix porte maintenant le nom de son usage dans le thème : bouton, fond teinté, page. Le choix pris se déplie. Il montre chaque token visé, sa couleur et son cran en Light et en Dark. Les autres choix tiennent sur une ligne : leur usage et leur token de fond.

Les crans viennent de la table du thème du kit, la même que remplit UCM Palettes. Un fond teinté vise le cran 100 en Light et 300 en Dark. Son texte vise le cran 800 en Light et 950 en Dark.

La question de l'intensité, douce ou vive, passe en premier. Les tokens montrés en dépendent.

7a · Composant : Tag sans tokens
  1. Un composant sans tokens propres reçoit « Préparer les tokens » dans son résumé.
7b · Composant : préparer
  1. La feuille pose les questions. Aucune réponse n'est cochée d'avance.
  2. L'intensité se choisit d'abord.
  3. Chaque choix nomme son usage dans le thème et les tokens qu'il vise.
  4. Les tailles se lient seules quand un seul token de layout a la valeur. Sinon une question.
  5. La liste des variables dit, pour chacune, le token visé ou la réponse qu'elle attend.
  6. Préparer reste inactif tant qu'une question reste.
7c · Composant : variables préparées
  1. L'alerte dit où continuer et que la préparation reste sur ce poste.
  2. La copie en texte n'apparaît qu'ici, quand la préparation est complète.
7d · Tokens : créer
  1. L'alerte nomme le composant et le nombre de variables à créer.
  2. La feuille liste chaque variable et le token qu'elle vise. Les chemins restent gris.
  3. Une variable qui existe déjà avec une autre cible le dit, et reste telle quelle.
  4. « Abandonner la préparation » demande une confirmation.
7e · Tokens : après Créer
  1. La ligne verte dit de publier la bibliothèque, puis de revenir au composant.
7f · Composant : lier
  1. Après la publication, Actualiser trouve les variables créées.
  2. Les comptes parlent de liaisons seulement.
  3. Une variable créée mais pas encore publiée a sa ligne grisée, sans case. La ligne dit pourquoi.

Réponse

« J'ai pas compris ce que ça veut dire et ce qu'est une variable qui attend. »

Une variable créée dans le fichier des tokens n'existe pour le fichier des composants qu'après la publication de la bibliothèque. Ici, 2 des 16 variables ont été créées après la dernière publication. Le plugin ne peut pas encore y lier un calque.

La ligne le dit maintenant : « Créée, pas encore publiée ». Elle n'a pas de case. Une alerte en bas de la carte dit le geste : publier Intencial Tokens, puis Actualiser.
