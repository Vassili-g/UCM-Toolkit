4d. Option a : une carte dans le panneau Recommandé

À quoi sert ce bouton

Sans lui, Architect ne propose aucune liaison pour une couleur en dur. Seul le fill d'un texte nommé title reçoit une proposition.

Le cas qu'il sert : les tokens de Button existent, mais les layers de ses 216 variants ne sont pas liés. Le designer lie un seul variant à la main, une dizaine de liaisons. Le bouton propose les liaisons des 215 autres, soit plus de deux mille gestes épargnés.

La préparation des tokens couvre un autre cas : elle crée les tokens qui manquent, puis lie les layers. Le bouton sert quand les tokens existent déjà, créés à la main ou après un renommage.

Où le mettre

La section Variants sert à choisir le variant affiché. Le bouton y apparaît sur tous les composants, même entièrement liés, où il ne propose rien.

OptionCe que voit le designer
a. Une carte dans le panneauUne carte dans Couleurs ou Tailles et forme, seulement quand des layers sont liés dans un variant et en dur dans d'autres. Le plugin prend comme modèle le variant le plus lié, et le nomme. « Proposer les liaisons » ajoute les corrections, à appliquer ensuite.
b. Un menu discretUn bouton « … » à côté du titre Variants. La phrase et l'exemple vont dans le résultat.
c. Retirer la fonctionLe designer lie chaque variant dans Figma, ou passe par la préparation des tokens.

Avis : a. La fonction apparaît là où le problème est signalé, et seulement quand elle propose quelque chose. Le designer n'a pas à choisir le modèle.

Le radius de .Ring En discussion, R-18

Les deux questions de la recette

.Ring sans collection, est-ce une erreur ? Non. FORMAT.md, « Composition et dépendances » : un set imbriqué sans instance de .componentRules « reste parcouru comme wrapper ou détail d'implémentation du parent ». .Ring est donc une pièce de Button. Le contrat de Button publie l'anneau dans ses propres strokes.ring.

Faut-il tous les composants dans la collection des tokens ? Non. CONCEPT.md, « La composition ne duplique pas », vise les composants unifiés : ceux qui ont leur propre contrat, parce qu'ils servent seuls. Un composant fait pour servir seul a sa collection. Une pièce interne comme .Ring n'en a pas besoin.

La question qui reste

Le radius de .Ring appartient donc à Button. La règle R-2 demande qu'il passe par un token de Button. Le kit rattache déjà à Button une liaison posée dans l'instance .Ring. Le constat suit la règle ; la règle est-elle la bonne pour une pièce interne ?

OptionCe que fait le designerCe qu'on gagneCe qu'on perd
1. Tokens d'anneau dans ButtonCrée ring-radius dans les tokens de Button, qui renvoie à Radius/lg, puis le lie sur l'instance .Ring de chaque variantR-2 reste sans exception. Button règle son anneau par taille sans toucher .RingUne liaison par instance. Le bouton de modèle les propose depuis un variant lié
2. Exception pour une pièce interneRien : .Ring garde Radius/lg dans son composant principalAucun geste dans FigmaLe contrat de Button cite un token de layout en direct. Changer l'anneau de Button oblige à modifier .Ring, et donc tous les composants qui l'emploient
3. .Ring devient un composant unifiéAjoute une instance de règles, une collection ring et un contrat.Ring se partage proprement entre composantsUn contrat et des tokens pour une pièce qui ne sert jamais seule

Avis. L'option 1 si l'anneau de Button doit pouvoir différer de celui d'un autre composant, ou suivre la taille du bouton. L'option 2 si l'anneau est le même partout et ne doit jamais varier : l'exception vise alors les layers d'un composant imbriqué dont le nom commence par . ou _, que Figma ne publie pas. Deux faits décident : .Ring sert-il à d'autres composants que Button ? Son radius doit-il suivre la taille du bouton ?

Accessibilité : variants désactivés et fond de page En discussion, R-19 et R-20

Les variants désactivés

WCAG 2.2, critères 1.4.3 et 1.4.11 : un composant inactif n'a pas d'exigence de contraste. Architect ne mesure donc pas les variants State=Disabled, et le dit dans une carte. CONTRIBUTING.md écarte pourtant tout message sans geste.

OptionPourContre
a. La carte d'aujourd'huiLe designer sait pourquoi ces variants n'ont aucun pointUne carte sans geste, à chaque analyse. Le designer apprend à survoler les cartes Information
b. Une ligne grise sous AccessibilitéL'information reste, au rang 3, sans carteUne ligne de plus sous la bande
c. RienSuit la règle des messages à la lettreUn designer peut croire que les variants désactivés ont passé le contrôle
d. Un seuil propre aux désactivésUn texte désactivé illisible reste signalé, en À vérifierUn seuil que WCAG ne donne pas : UCM devrait le décider et l'écrire dans le kit (R-24)

Avis : b. L'option d serait un choix de produit, à décider à part.

Le fond d'un variant sans fill

Le kit remonte les fills des parents du layer, dans le variant seulement. Un variant Outlined n'a pas de fill opaque : le fond reste inconnu. En pratique, ce composant se pose sur le fond de la page, qui change avec le mode. UCM nomme ce fond : elevation/page dans le thème.

Source du fondPourContre
A. elevation/page du thèmeLe fond réel du produit, une valeur par mode. Suit UCM Palettes : le fond de page prévu est #f8fafc, pas #FFFFFFDemande un thème UCM au catalogue
B. Le fond de la page FigmaToujours disponibleLe fond du canvas, choisi pour travailler, pas celui du produit. Une seule valeur, sans mode
C. Une valeur fixe par modeSimpleFausse dès que Palettes change le fond de page
Mode mesuréPourContre
Le mode affiché dans FigmaLa mesure correspond à ce que le designer voitUn défaut en Dark passe inaperçu tant que le designer travaille en Light
Chaque mode du thèmeLe composant sert dans les deux modes. La carte dit lequel échoue. Les autres mesures de contraste se font déjà par combinaison de modesDeux mesures par paire

Avis : A, dans chaque mode du thème, avec B en repli quand le fichier n'a pas de thème UCM. Une question de plus : un bouton Outlined se pose aussi sur une carte, elevation/raised. Faut-il mesurer aussi sur ce fond (R-23) ?
