1Le concept UCM

Défini dans CONCEPT.md et ROADMAP.md.

Dans un design system, un composant existe à plusieurs endroits : la maquette Figma, le code, les tokens et la documentation. Ces versions divergent quand aucun outil ne les compare. Une variante dessinée manque au code, un token cité a disparu, et l'équipe ne sait plus quelle version fait foi.

UCM publie pour chaque composant Figma un contrat JSON, rangé à côté de son code dans le repository de l'application. Le contrat cite chaque couleur et chaque dimension par le nom de son token, et tokens.json donne la valeur de chaque token. À chaque pull request, le CI compare le contrat, les tokens et le code.

  1. FigmaLe designer dessine le composant et prépare ses variables avec les plugins UCM.
  2. Contrat et tokensUn plugin publie <Id>.contract.json et tokens.json par pull request.
  3. RepositoryLe contrat est rangé à côté du code du composant.
  4. CIucm check compare le contrat, les tokens et le code à chaque pull request.

Les deux promesses

Robustesse

Un écart entre Figma et le code est détecté avant la fusion, avec un diagnostic qui dit quoi corriger.

Confiance

Un développeur ou un agent emploie un composant sans inventer son API visuelle, car le contrat donne ses props, ses variantes et ses tokens.

Chaque piste de la feuille de route sert l'une des deux promesses.

Les principes

Une information, un propriétaire
Figma fait foi pour le visuel : tokens, variantes, états, dimensions, icônes et règles d'usage. Le code fait foi pour le comportement, les événements et l'accessibilité. Le CI juge si les deux s'accordent.
Le composant unifié
Le contrat et le code du composant vivent dans le même dossier. Les tokens restent dans un fichier DTCG commun.
Le code écrit contre le contrat
Le développeur écrit le composant à partir du contrat. Le build en dérive des types et des variables CSS, et le code ne lit jamais le contrat à l'exécution.
Full UCM
Les outils suivent l'architecture de référence du kit, et seul le plugin d'export accepte en option toute structure de variables. UCM vise un design system neuf qui suit ses règles.ucm check juge l'architecture de tokens.json en information, sans rien bloquer.

Ce qu'UCM ne fait pas encore

  • Aucun outil ne compare le rendu d'un composant à son contrat ou à Figma (P9, P10, P20).
  • Une pull request rouge reste fusionnable, car le plan GitHub actuel n'offre pas la protection de branche (P17).
  • Aucun contrat réel n'est encore au format {{contrat}}. Les {{recette-contrats:nombre}} contrats de recette sont en {{recette-contrats:version}} (P1).

Ce qu'il ne voit pas

  • Une union plus large que le contrat.
  • Une dépendance rendue par .map().
  • Le défaut d'un axe dans le code.
  • Les couleurs, tailles et polices rendues.

  • Interface absente.
  • Fonction absente.

  • Valeur du contrat que le code n'offre pas.
  • Booléen jamais lu.
  • Enum sans effet.
  • Nombre d'occurrences d'une dépendance faux dans le JSX.

3Le parcours d'un composant

Défini dans CONCEPT.md §5 et le README.md de chaque outil.

Le parcours suit un composant de ses premières couleurs dans Figma jusqu'à son code, en huit étapes. Chaque étape nomme qui agit, avec quel outil, et ce qu'elle produit. Cliquez sur une étape pour afficher son détail.

Le designer, dans Figma
La forge et le CI
Le développeur, dans le repository

1Couleurs

Qui
Le designer, dans Figma, avec UCM Palettes
Ce qui se passe
Palettes calcule pour chaque couleur de marque et chaque statut une palette Light et Dark de {{crans:nombre}} crans, en intensité Soft ou Vivid. Chaque palette tient les {{garanties:nombre}} garanties de contraste.
Ce qui en sort
Les variables de couleur de la collection primitives, et une planche par palette.

2Variables à la main

Qui
Le designer, dans Figma, sans outil
Ce qui se passe
Le designer pose les collections brands, utility, layout et typography : les palettes de marque, le neutre et les statuts, les tailles, les rayons et les réglages de texte. Architect crée ensuite les alias de brands et de utility vers primitives (piste P21, livrée). Aucun outil n'écrit layout ni typography.
Ce qui en sort
Des alias vers les primitives, et les tailles et les textes du design system.

3Thème et noms

Qui
Le designer, dans Figma, avec UCM Architect, vue Tokens
Ce qui se passe
Architect renomme les variables selon la convention choisie. Il vérifie et complète les {{theme:variables}} variables du thème, leurs crans, leurs alias de mode et leurs scopes.
Ce qui en sort
La collection theme, qui vise brands et utility, et des noms conformes à la grammaire.

4Composant

Qui
Le designer, dans Figma, avec UCM Architect, vue Composant
Ce qui se passe
Architect analyse un jeu de variants : liaisons, tailles, texte, icônes, contrastes, cibles et règles d'usage. Il propose les seules corrections exactes, pose une question pour le reste, puis prépare les tokens du composant.
Ce qui en sort
Les variables du composant dans components, et des calques liés aux tokens de leur composant.

5Publication

Qui
Le designer, avec UCM Contract Exporter, vers la forge
Ce qui se passe
L'Exporter publie tokens.json d'abord, puis le contrat du composant. Chaque fichier part sur sa branche, avec sa pull request, sur GitHub ou gitlab.com. L'Exporter ne fusionne jamais seul.
Ce qui en sort
tokens.json au format DTCG et <Id>.contract.json en contrat {{contrat}}, dans le repository de l'application.

6Contrôle

Qui
Le CI de la forge, avec ucm check de la CLI
Ce qui se passe
À chaque pull request, ucm check lit le contrat, tokens.json et le code. Un contrat illisible bloque la fusion. Un token absent ou un écart du code avertit.
Ce qui en sort
Un rapport en commentaire de la demande, montré dans la partie 6.

7Code

Qui
Le développeur ou son agent, avec la CLI et l'adaptateur TypeScript
Ce qui se passe
ucm tokens css produit la feuille CSS des tokens et de leurs modes. L'adaptateur génère les types des variantes. Le développeur écrit le composant contre le contrat, avec ucm guide et la skill ucm-implementer. L'adaptateur compare ensuite les props du code à celles du contrat.
Ce qui en sort
Le composant codé, et sa parité contrôlée en avertissement.

8Rendu

Qui
Aucun outil
Ce qui se passe
Aucun outil ne compare le rendu du composant dans un navigateur à son contrat ou à Figma. P9 monte les stories, P10 compare le rendu et P20 le fait bloquer.
Ce qui en sort
Aucun constat.

Une étape en pointillés gris est un geste fait à la main. Une étape en pointillés roses est un contrôle absent.

4L'architecture des variables Figma

Défini dans packages/kit/src/referentiel/ et packages/kit/src/emplois/.

Dans Figma, une variable porte une couleur ou un nombre, que le designer lie à un calque. Une collection de variables regroupe des variables qui partagent les mêmes modes, comme Light et Dark. Un alias est une variable qui vise une variable d'une autre collection au lieu de porter une valeur. UCM range les variables d'un design system en {{collections:nombre}} collections, des valeurs brutes de primitives jusqu'aux variables de chaque composant. Le kit écrit ces définitions une seule fois, et Palettes, Architect et l'Exporter les importent.

Les {{collections:nombre}} collections de variables

Défini dans packages/kit/src/referentiel/architecture.ts.

Suivre une valeur d'un composant

Une couleur part d'une primitive, que brands vise, puis theme, puis la variable du composant. Le neutre et les statuts passent par utility au lieu de brands.

  1. primitives/color/terracota/soft/light/700
  2. brands/primary/light/700
  3. theme/primary/solid/default
  4. components/{Composant}/color/primary/default/background

Une taille part d'une valeur posée dans layout, ou d'une primitive que layout vise. La variable du composant vise la variable de layout.

  1. primitives/…
  2. layout/radius/md
  3. components/{Composant}/size/md/radius

Un réglage de texte part d'une primitive, que typography vise, puis une variable de texte du composant.

  1. primitives/font-size/base
  2. typography/body/md/font-size
  3. components/{Composant}/…

Une flèche va de la collection qui fournit la valeur à la collection dont les variables la visent par alias. Le mot en italique restreint le type : les couleurs de components viennent de theme, ses tailles et ses textes de layout et typography.

Palettes écrit la collection.

Architect crée et corrige ses variables.

Aucun outil n'écrit la collection, le designer pose ses variables à la main.

scope

Les variables d'une collection « scope oui » portent des scopes Figma, qui limitent les champs où le designer peut les lier. Une collection « scope non » sert seulement de source aux alias.

5Le contrat

Défini dans packages/kit/src/format/types.ts, docs/format/FORMAT.md et CONCEPT.md §4.

Le contrat est le fichier JSON que l'Exporter publie pour un composant, à côté de son code. L'extrait vient de {{bouton:chemin}}, le contrat de recette du Button exporté de Figma ({{bouton:octets}} octets, {{bouton:props}} props, {{bouton:variants}} variants).

{
  "name": "Button",
1  "meta": { "contractVersion": "{{bouton:version}}", "coverage": { "portable": "complete" } },
2  "props": {
    "color": { "type": "enum", "values": ["secondary", "primary", "info", "success", "warning", "error"] },
    …
  },
3  "variants": [
    {
      "values": { "color": "primary", "variant": "contained", "state": "default" },
4      "tokens": {
        "background": "{components.button.colors.primary.contained.default.background}",
        "foreground": "{components.button.colors.primary.contained.default.foreground}"
      }
    },
    …
  ],
5  "stateModel": {
    "axis": "state",
    "precedence": ["disable", "press", "focus", "hover", "default"]
  },
6  "intent": {
    "usage": "Action déclenchant une opération ; le choix des variantes dépend de l'importance et du contexte."
  }
}
  1. 1
    meta.coverage.portable vaut complete ou partial. Il passe à partial quand l'Exporter ne sait pas décrire une propriété Figma.
  2. 2
    props : les props que le code doit exposer. La parité les compare à celles du composant TypeScript.
  3. 3
    variants : une entrée par variant dessiné dans Figma, jamais une matrice cartésienne.
  4. 4
    tokens : un nom de token, jamais une valeur. La valeur vit dans tokens.json.
  5. 5
    stateModel : l'état qui l'emporte quand deux s'appliquent. Ici disable passe avant press, focus, hover et default.
  6. 6
    intent : la règle d'usage que le designer écrit dans Figma.

Ce contrat {{bouton:version}} écrit colors et error. La grammaire actuelle écrit color et danger, et Architect proposerait ces deux renommages.

Ce que le contrat garantit

Tokens en références
Le contrat cite {components.button.color.primary.contained.default.background}, jamais la valeur. Le même chemin va de Figma au code.
Noms traçables
Le nom Figma lisible reste dans le contrat, à côté de l'identifiant de code.
Composition sans copie
Un composant composé cite ses dépendances sans recopier leurs tokens ni leur structure.
Contrat avant le code
Le contrat se fusionne avant l'implémentation. La parité s'applique dès que le code existe.
Divergences visibles
Une information ambiguë produit un diagnostic. Seules les préconditions d'un contrat cohérent bloquent l'export.
Contrat autosuffisant
Le contrat se lit sans Figma. Une perte de projection est écrite dans meta.diagnostics et passe meta.coverage.portable à partial.
Champs normatifs
Chaque champ oblige le code, et un contrôle peut le lui opposer. Seul samples est indicatif : il montre le contenu de la maquette.

Composition et règles d'usage

Défini dans packages/kit/src/referentiel/composition.ts.

Testées dans cet ordre. Dépendance : ses règles la nomment. Wrapper de dimensions : ses dimensions sont liées à layout. Pièce interne : son nom commence par . ou _, sans contrat ni collection. Détail : le reste.

Seuls divider, ring et icon désignent un layer par son nom. L'icône est une instance du composant Icon. Son remplissage suit le token icon ou foreground de l'hôte, sa Size la taille du variant.

Le comportement, les événements, le clavier, l'accessibilité et les attributs natifs : le code en répond. Les assets et les images. Un mode fixé sur un calque. L'adresse du fichier Figma, qu'un Storybook comparé à Figma réclamera sous la clé figmaFileKey de ucm.config.json (P9).

Dans la pull request, avec ucm check

Défini dans packages/kit/src/lecteurs/diagnostic-parite.mjs et packages/kit/src/lecteurs/verdict-bilan.mjs.

Une pull request (merge request sur GitLab) propose d'intégrer une branche dans main. L'Exporter en ouvre une pour chaque contrat ou tokens.json exporté depuis Figma, et un développeur en ouvre une quand il modifie le code. À chaque envoi sur la branche, le CI lance ucm check, qui écrit son rapport en commentaire de la pull request et fait échouer le job quand le rapport bloque. Dans l'exemple, une pull request modifie Button.tsx, qui n'a pas de prop size.

À revoir par le mainteneur

L'exemple de droite est une pull request de code : le développeur modifie Button.tsx sans ajouter size. Une pull request du designer qui ne change que Button.contract.json passe, et le composant devient « en retard sur son contrat » (V-05 de P19).

Le point à trancher est V-11. Un développeur qui touche le code d'un composant en retard, pour corriger un bug par exemple, est bloqué tant qu'il ne rattrape pas le contrat ou ne pose pas de dérogation.

La colonne de gauche décrit encore l'ancienne CLI, qui avertissait sans bloquer. La CLI {{version:cli}} applique déjà la règle de droite, sauf le bouton grisé, qui attend la protection de branche de P17.

Ce que ucm check fait de chaque écart aujourd'hui

bloque

  • Un contrat illisible, incomplet ou hors de la fenêtre {{contrats:fenetre}}.
  • Une composition cassée, quand le contrat d'un imbriqué manque ou qu'un cycle apparaît.
  • Un token de typographie dont le type est faux.
  • Un fichier de tokens absent ou illisible.

avertit sans bloquer

  • Un token cité par le contrat et absent de tokens.json.
  • Un écart de parité entre les props du code et le contrat.
  • Le contraste des couleurs du contrat, en information seulement, car ucm check ne sait pas si un texte est grand.

non vérifié

  • Le rendu dans un navigateur : couleur, dimensions, typographie, structure et ordre (P9, P10, P20).
  • Une valeur écrite en dur dans le code (P6).
  • La fusion d'une pull request rouge, que seule une protection de branche empêche (P17).

bilanEstBloquant (lecteurs/verdict-bilan.mjs) ne compte ni les tokens absents ni la parité.

    8Expliquer UCM à des développeurs

    Défini dans CONCEPT.md et docs/guides/RECETTE.md.

    Réponses tirées du dépôt et des décisions du mainteneur.

    Pourquoi un contrat JSON plutôt que l'API Figma ou Code Connect ?
    Le CI lit le contrat sans accès à Figma, et le contrat est versionné à côté du code. Code Connect relie un composant Figma à son code sans décrire les obligations visuelles. Les deux se complètent.
    L'API du kit est-elle stable ?
    Une seule porte est promise aux modules, @ucm-kit/core/modules. Un test refuse qu'elle change sans entrée au journal du kit, et le chiffre du milieu de la version monte à chaque rupture. Les autres portes servent les outils UCM et changent librement. Le guide docs/guides/MODULES.md le détaille.
    Que se passe-t-il quand le designer change un token ?
    Sa valeur change dans tokens.json, et la pull request passe. Le code suit une fois la feuille régénérée par ucm tokens css. Un token cité par un contrat puis retiré avertit aujourd'hui, et bloquera une fois la règle de blocage codée (P19).
    Un contrat peut-il arriver avant le code ?
    Oui. Il est fusionné « à implémenter », et la parité s'applique dès que le composant existe.
    Comment tester sans Figma ?
    npm test couvre le moteur, les lecteurs sur des contrats fabriqués et la CLI sur des repositories temporaires. Ce qui touche Figma et une vraie forge se rejoue dans UCM-Playground, l'application de recette sur GitHub. Un agent ne peut pas exporter depuis Figma.
    Peut-on modifier le kit ?
    Le cœur a un seul mainteneur, et un changement du kit se décide avec lui. Les modules importeront seulement l'API que P3 fige.
    Glossaire les termes de cette page
    Adaptateur
    Le module qui lit le code d'un langage pour le comparer au contrat.
    Alias
    Une variable qui vise une autre variable au lieu de porter une valeur. Un alias de mode vise une variable différente en Light et en Dark.
    API publique
    Les fonctions et types qu'un paquet promet de garder stables. Le reste peut changer sans prévenir.
    Axe, variante, variant
    Un axe est une propriété de variant (Color, Size, State). Une variante est une valeur d'axe (primary). Un variant est une combinaison de variantes.
    CI
    Les contrôles qui tournent à chaque pull request, sur GitHub Actions ou GitLab CI. Ici, ucm check.
    CODEOWNERS
    Un fichier GitHub qui désigne qui doit approuver une pull request selon les fichiers touchés.
    Codex
    L'agent de code d'OpenAI. Il lit AGENTS.md à la racine du dépôt.
    Collection de variables
    Un groupe de variables Figma qui partagent les mêmes modes, comme Light et Dark. UCM en attend {{collections:nombre}}.
    Constat
    Une remarque d'Architect ou de l'Exporter sur un composant, avec un code de {{codes:plage}} et un type d'alerte. Les {{codes:nombre}} codes.
    Contrat
    Le fichier <Id>.contract.json que l'Exporter écrit pour un composant Figma, avec ses props, ses variants et le token de chaque couleur et dimension.
    Contrat {{contrat}}
    Le numéro du format du contrat. ucm check accepte les contrats {{contrats:lus}}.
    Contrats de recette
    Les {{recette-contrats:nombre}} contrats réels Button, Alert, TileLink et StressTest, exportés depuis Figma, que les tests du dépôt font lire par les lecteurs.
    Cran
    Une des {{crans:nombre}} nuances d'une palette, numérotées de 50, la plus proche du fond, à 950.
    Dépôt, repository
    Dans cette page, le dépôt désigne UCM-Toolkit et le repository désigne celui de l'application.
    Dérogation
    Une exception motivée qu'un développeur écrit pour laisser passer un écart, en attendant la relecture du designer.
    Diagnostic
    Un message de l'Exporter rangé dans le contrat, sous meta.diagnostics. C'est toujours un avertissement.
    DTCG
    Design Tokens Community Group, auteur du format standard de tokens.json.
    En retard sur son contrat
    Se dit d'un composant dont le code ne suit pas encore son contrat. Cette expression est réservée à ce cas.
    Épingler
    Écrire une version exacte, sans ^, pour que npm n'en installe jamais une autre.
    Export, symbole
    Un nom qu'un fichier rend utilisable par d'autres fichiers.
    Forge
    Le service qui héberge le repository et ses pull requests, GitHub ou GitLab.
    Full UCM, agnostique
    Un outil full UCM exige l'architecture de référence : {{collections:nombre}} collections, {{crans:nombre}} crans, {{theme:variables}} variables de thème. Un outil agnostique accepte toute structure.
    Garantie
    Un contraste minimal entre deux variables du thème. G1 : le texte d'un bouton plein atteint 4,5:1 sur son fond. Tableau des {{garanties:nombre}} garanties.
    Imbriqué
    Une instance d'un autre composant, placée dans le composant. Les 4 sortes d'imbriqué.
    Intensité (profil dans le code)
    Le réglage de saturation d'une palette, Soft ou Vivid. Vivid prend {{palettes:part-vivid}} de la saturation possible, Soft {{palettes:part-soft}}. Une palette grise n'a qu'une intensité, dite unique.
    Lecteur
    Une fonction du kit qui lit un contrat ou tokens.json et rend un bilan. La CLI s'en sert dans le CI.
    Liaison
    Ce qui relie une propriété d'un calque à une variable.
    Linter
    Un outil qui lit le code sans l'exécuter et signale les écritures interdites. ESLint est le linter standard de JavaScript et TypeScript.
    Lockfile
    package-lock.json fige les versions installées. Le workflow n'installe les dépendances que s'il existe.
    Mode, thème
    Un mode est une colonne de valeurs d'une collection Figma, par exemple Light et Dark. Le thème est la collection theme, qui porte les {{theme:variables}} variables d'usage.
    Module consommateur
    Un outil installé dans le repository de l'application, comme le linter, le générateur de stories ou le vérificateur de rendu, qui lit les contrats.
    Monorepo
    Un seul dépôt Git qui contient plusieurs paquets, comme UCM-Toolkit.
    Normatif, indicatif
    Un champ normatif oblige le code, et un contrôle peut le lui opposer. Un champ indicatif montre seulement le contenu de la maquette.
    Parité
    La parité compare les props du contrat à celles du composant TypeScript.
    Perte de projection
    Quand l'Exporter ne sait pas décrire une propriété Figma dans le format, il l'écrit dans meta.diagnostics et passe meta.coverage.portable à partial.
    Piste, rang
    Une piste est un chantier proposé. Le rang est son ordre de priorité, de 0 à 5.
    Planche
    Un cadre Figma où Palettes dessine les nuances d'une palette.
    Point d'entrée
    Un chemin d'import du kit, comme @ucm-kit/core/lecteurs.
    Protection de branche
    Le réglage de la forge qui interdit de fusionner une pull request dont le CI est rouge. Sans lui, un échec reste un avis.
    Pull request, merge request
    Le nom GitHub et le nom GitLab de la proposition d'intégrer une branche dans main. Le CI y lance ses contrôles et la revue s'y fait avant la fusion.
    Recette de palette
    L'ensemble des réglages d'une palette, que Palettes enregistre dans le fichier Figma.
    Recette externe
    Le rejeu, hors du dépôt, de Figma, d'une forge et d'une vraie pull request, dans UCM-Playground pour GitHub et dans un projet GitLab de recette.
    Réglage global, Color shift
    Le Réglage global change la teinte, la saturation et la luminosité de toute la palette. Le Color shift les fait varier le long de la rampe, du cran clair au cran foncé.
    Règles d'usage
    Le bloc .componentRules posé à côté du composant dans Figma pour dire quand l'employer. L'Exporter les publie dans intent.
    Régression visuelle
    Comparer une capture du rendu à une capture de référence validée, pour repérer un changement non voulu.
    Schéma JSON
    Un fichier qui décrit la forme permise d'un JSON.
    Scope
    Ce qui limite les champs où le designer peut lier une variable : remplissage, contour, rayon.
    Sens normal, sens inverse
    Deux choix de texte des boutons. Light blanc et Dark noir donnent le sens normal. Light noir et Dark blanc donnent le sens inverse, qui change le cran visé par certaines variables du thème.
    Slot, instance-swap
    Un slot est un emplacement où l'on dépose un autre composant. Un instance-swap est une propriété Figma qui échange une instance contre une autre.
    Storybook, story
    Un atelier qui affiche chaque composant isolé. Une story montre un composant dans une combinaison de props.
    Token
    Une variable Figma publiée sous son chemin, comme theme/primary/solid/default.
    Variable primitive
    Une variable qui porte une couleur ou une taille brute. Les autres collections la visent par alias.
    Verdict
    Le mot a trois sens. Dans Palettes, le verdict dit si la palette tient les {{garanties:nombre}} garanties. Dans l'Exporter, le « Contrôle avant publication » prend sa place. Dans ucm check, le verdict dit si la pull request peut fusionner.
    Version 0.x
    En semver, une version sous 1.0 n'engage aucune compatibilité. On épingle alors la version exacte.
    Vue Tokens, vue Composant
    Les deux vues d'Architect. La vue Tokens parcourt les variables du fichier. La vue Composant analyse un jeu de variants.
    WCAG, APCA
    WCAG 2 est la norme de contraste en vigueur, avec 4,5:1 pour un texte. APCA est la méthode prévue pour WCAG 3.
