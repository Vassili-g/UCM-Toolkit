# Diagnostics

- **Une donnée facultative incomplète avertit ; les préconditions explicitement définies dans la spec bloquent.** Unique exception, motivée dans [l'échantillon](./echantillon.md#échantillon-de-maquette) : il ne réclame jamais rien.
- **`ucm check` vérifie que chaque propriété d'un composant a une variable ; l'usage des couleurs n'y est qu'une information.**
- **Le diagnostic des contrastes s'applique à tout `tokens.json`, sans nom de collection imposé.** Signale une couleur `foreground` ou `icon` sous 4,5:1, `border` ou `ring` sous 3:1, contre son fond, en sévérité `info`, sans jamais bloquer la fusion. Fond = plus long préfixe du chemin de la couleur qui porte un `background` (FORMAT.md, section 2). Mesure à 8 bits dans chaque marque et chaque thème ; couleur hors de sRGB ou translucide : non jugée. Bornes : lit seulement le premier alias d'un token de composant ; le contrat ne dit pas si un texte est en grand corps, où le seuil descend à 3:1 ; un faux signal reste une information. Autorité : `diagnostic-contrastes.mjs`. Tests : `kit/tests/diagnostic-contrastes.test.mjs`, un contrat par constat et un contrat conforme. Spec : [spec](../../../docs/format/FORMAT.md#2-tokens-de-variantes)
- **`ucm check` juge l'architecture de `tokens.json` avec les contrôles d'UCM Architect, en information seulement.** `controlerLIntegriteUcm` et `controlerLeCatalogue` lisent la projection du fichier. Seul l'Exporter est agnostique : ce contrôle est actif sans option. Aucun constat n'entre dans `bilanEstBloquant`, donc une demande de tokens seuls reste verte. Le rapport groupe les constats par genre, avec leur nombre et 3 exemples de 120 caractères au plus, en dernière section ; les liens de `brands` et de `utility` y comptent les variables sans lien, les familles sans palette, les couleurs de charte sans cran et les palettes à compléter, sans rien choisir. Aucune collection reconnue : une seule ligne, sans constat. Section absente d'une demande qui ne touche pas `tokens.json`, sauf contrôle sans `--base`. Borne : les jetons de type composé ne sont pas des variables Figma, aucun contrôle ne les juge ; un fichier UCM sans collection `theme` reconnue reçoit l'information `theme-non-reconnu`. Autorité : `diagnostic-architecture.mjs` ; `kit/src/controles/projection-dtcg.ts` `catalogueDepuisTokens`. Tests : `kit/tests/diagnostic-architecture.test.mjs`, `kit/tests/projectionDtcg.test.ts`, `cli/tests/check.test.mjs`.
- **On avertit seulement sur ce qu'on publie.** Valeur que le contrat va jeter (dimensions du calque de référence quand `sizes` existe) : ni relevée ni signalée.
- **Un avertissement s'adresse au designer : nom Figma exact, ce qui manquera, geste à faire.** Les trois sont exigés ; un constat sans geste n'est pas un avertissement et ne s'écrit nulle part.
- **Un message qui vise la racine de chaque variant du set exporté ne nomme aucun calque** : le nom change d'une racine à l'autre, la phrase s'écrit une fois pour toutes (`plugin-socle/src/composant/contract/localisation.ts` `pousserPourLesVariants`).
- **Un point bloquant se lit en tête de la liste, quel que soit son rang d'arrivée.** Le contrat est déjà faux, là où un avertissement le laisse exact. Moteur : en tête de `meta.diagnostics` (la demande de fusion coupe sa liste par la fin). Interface : insère avant le premier avertissement, sans trier les autres. Tests : `tests/interface/interface.test.mjs`.
- **Un composant imbriqué sans ses règles se signale dans le contrat.** Composant publié, non contracté, pas une icône : point bloquant, publié dans `meta.diagnostics` et la demande de fusion en `UCM_PORTABLE_PROJECTION_WARNING` (le contrat n'a pas la dépendance qu'il devrait réutiliser). La création des règles relit le relevé que l'export lui rend. Le verdict compte ce que la liste montre. Autorité : `plugin-socle/src/composant/contract/imbriques.ts` `releverLesImbriques`, unique relevé.
- **Les trois parties voyagent séparées, du site d'émission à l'interface.** Un site écrit un `Constat` (`plugin-socle/src/composant/contract/localisation.ts`), jamais une phrase. Un point bloquant porte en plus la liste que son titre annonce (`elements`), écrite par la phrase après le titre. La phrase compacte de `meta.diagnostics`, de la demande de fusion et du journal en dérive (`phraseDe`), sans seconde rédaction ; l'interface met les parties en page et ne recoupe rien. Tests : deux lois dans `tests/loiDesParties.test.ts`, l'une lit la source et refuse un message écrit ailleurs qu'à l'autorité, l'autre lit la sortie du moteur et refuse un message sans ses parties. Spec : [§avertissements]
- **Un export remonte seulement ce qui demande une décision.** Trois portes, rien d'autre. Transformation entièrement prise en charge : silencieuse dans le plugin, la demande de fusion et `meta.diagnostics` ; la spec et les tests du format portent cette règle. Spec : [§avertissements]
- **Le rapport CI suit la règle de l'export : il parle seulement d'une demande de fusion qu'il concerne.** Le contrôle tourne sur toutes, sans filtre de chemin : la conformité se casse aussi dans le code seul.
- **Une demande qui ne touche ni contrat, ni `tokens.json`, ni `ucm.config.json`, ni l'implémentation résolue d'un contrat reçoit le rapport sans objet** : une ligne qui remplace un verdict devenu faux, jamais un commentaire créé. Un refus s'écrit toujours en entier. Le marqueur `<!-- ucm-sans-objet -->` porte ce périmètre jusqu'aux deux publicateurs. Autorité : `perimetre-rapport.mjs`.
- **Le dernier modifié répond : le verdict de `ucm check` dépend de la demande, de l'adaptateur attendu et des dérogations.** Demande du designer (contrats et tokens seuls) : jamais refusée pour du code ; tokens seuls, refusée seulement si `tokens.json` est illisible, jamais par un échec relayé des tests du repository ; contrats, refusée pour un contrat invalide ou à token absent seulement s'il est modifié par elle. Demande de code ou contrôle sans base : un écart de parité ou un constat du code bloque, sauf contrat ou `tokens.json` plus récent que le code (« en retard ») ou dérogation valide de `.ucm/derogations.json` (elle tombe quand `meta.exportedAt` change) ; un adaptateur attendu absent, cassé, ancien (sans `lecteurDuCode`) ou qui ne lit pas un fichier du composant bloque, une technologie sans adaptateur avertit. Un état qui bloque ne dit jamais qu'il ne bloque pas, dans le rapport comme dans le terminal. Le rapport d'une demande de contrat liste les dérogations à valider. Borne : sans `rangs`, `controlerRepository` donne rang 0 aux fichiers de `cheminsModifies` et 1 aux autres, donc aucun retard ; la mesure de Git est celle de `cli/src/rangs.mjs` (`mesurerLesRangs`, premier parent, fichier de demande ou copie de travail au rang 0, clone superficiel refusé en 2 même sans contrat). Une panne de lecture de l’adaptateur attendu devient `casse`, sans erreur d’invocation ; une demande du designer reste jugée. Les écarts du code restent visibles dans le rapport des tokens seuls, même sans composant touché. Le rapport lit `bloquantPar` (contrat, tokens, parité, code) et n'en recalcule rien. Autorité : `kit/src/lecteurs/verdict-bilan.mjs` `verdictDeLaDemande`. Tests : `kit/tests/verdict-demande.test.mjs`, `kit/tests/controleRepository.test.mjs` (« le rapport et le verdict disent la même chose »), `cli/tests/verdictGit.test.mjs`.
- **Les listes, les codes et les messages du contrôle du code vivent seulement dans `kit/src/lecteurs/controle-du-code-listes.mjs`.** Familles, propriétés, valeurs neutres, codes, limites, raisons. L'inventaire, le guide `docs/guides/LINTER-UCM.md` et le plugin du développeur les lisent ou les nomment, sans les recopier. Réglage : skill `regler-le-linter`. Tests : `kit/tests/controle-du-code-listes.test.mjs`, `tests/ecrituresDesAidesJugees.test.mjs`.
- **`lecteurDuCode` de `@ucm-kit/adapter-typescript` est la seule lecture du code, pour le plugin ESLint comme pour `ucm check`.** Il relève sans juger ; le juge est `kit/src/lecteurs/controle-du-code.mjs` `preparerControleDepuis`, appelé par `preparerControle` et par `controlerRepository`. Borne : la liste des propriétés sans unité de React vit seulement dans `adapter-typescript/src/usages.mjs`. Tests : `adapter-typescript/tests/usages.test.mjs`, `kit/tests/controleRepository.test.mjs` (S5).
- **Une dérogation d'un constat du code s'applique dans le juge, par `appliquerDerogations`, pour l'éditeur comme pour `ucm check`.** Elle couvre un écart exact (`valeur-en-dur` : fichier et valeur ; `token-inconnu`, `repli-en-dur` : fichier et référence) et tombe au réexport du contrat. `ucm deroger` l'écrit ; un commentaire `eslint-disable` qui nomme une règle UCM donne `desactivation-interdite`, bloquant et non dérogeable. Autorité : `kit/src/lecteurs/derogations.mjs`. Tests : `kit/tests/derogations.test.mjs`, `cli/tests/deroger.test.mjs`.
- **`meta.diagnostics` est l'unique propriétaire des messages publiés dans le contrat.** Liste lisible : `diagnostics[].message`, sans filtrer sur `severity`.
- **Le corps de la demande de fusion a deux zones.** En-tête : identité de ce qui est déposé, soit le chemin, puis le schéma de contrat (contrat) ou la version du format de tokens (`tokens.json`). Liste : seulement des gestes. Ce que le plugin compte = ce que la demande liste = ce que `meta.diagnostics` publie. Spec : [§avertissements]
- **`meta.figma.url` est absent des contrats produits aujourd'hui, état normal.** Plugin distribué par la Community : sans `enablePrivatePluginApi`, donc sans `figma.fileKey`. Champ optionnel au schéma (un contrat plus ancien le porte encore), son absence ne produit aucun diagnostic. Traçabilité : `fileName` et `nodeId`, annoncés dans le corps de la demande de fusion. Spec : [spec](../../../docs/format/FORMAT.md#métadonnées)
- **Le numéro annoncé dans l'en-tête est lu dans le fichier déposé** : `kit/src/format/version.ts` `versionDeContrat()` (contrat), `kit/src/format/tokens.ts` `etatDuFormatDeTokens()` (`tokens.json`). Jamais `CONTRACT_VERSION` ni `TOKENS_FORMAT_VERSION`. Spec : [§forge]
- **Un export identique n'ouvre jamais une seconde demande de fusion.** Immobilité jugée sur la branche de base **et** sur les demandes d'export encore ouvertes (`src/depot.ts` `exportsEnVol()`), sur l'une et l'autre forge. Le verdict porte l'endroit où le contenu identique a été trouvé ; le journal le dit. Contenu différent pendant qu'une demande est ouverte = réexport après correction, geste normal, non refusé. Spec : [§forge]
- **Un avertissement entre dans le corps de la demande en Markdown ; chaque forge y neutralise ses formes actives.** `sansLienAutomatique()` publie en `code` `@nom` et `#123` sur GitHub (`src/forges/github.ts`), et en plus `!123`, `~label`, `%jalon`, `$123`, `&123`, la référence croisée et une ligne commençant par `/` sur GitLab (`src/forges/gitlab.ts`), où elle serait exécutée comme action rapide. Le rendu Markdown du kit ne sait pas sur quelle forge le rapport part : il neutralise les formes des deux. Spec : [§forge]
- **Un jeton part seulement vers le dépôt qui l'a reçu.** Il voyage dans l'entrée de son adresse, écrite en une seule écriture de `depots`. L'adresse d'une entrée enregistrée ne change plus : le sandbox refuse une modification qui la changerait. `src/config.ts` `validateSettings()` valide chaque entrée avec son propre jeton ; ouverture, pré-vol, publication et enregistrement y passent tous. Une file du sandbox ordonne les écritures de la configuration : une modification ne fait pas revenir une entrée supprimée dans la même fenêtre. Spec : [§forge]
- **Tout texte du plugin qui nomme une forge, sa demande ou son jeton lit `src/forges/termes.ts` ; aucun message ne teste la forge.** La galerie tient la frontière dans les deux sens : un état GitLab n'affiche aucun mot de GitHub, et l'inverse. État `mixte` (liste des dépôts avec les deux forges) : chaque message vérifié contre la forge de son sujet, soit l'entrée désignée pour `depot-teste`, la clé de destination d'un résultat d'opération, le dépôt actif pour le reste. Tests : `tests/galerie.test.ts`. Spec : [§forge]
