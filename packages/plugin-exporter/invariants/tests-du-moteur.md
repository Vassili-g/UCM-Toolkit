# Tests du moteur

- **Le moteur ne se teste sur aucun contrat commité.** Un `.contract.json` appartient au repository qui le consomme, à côté du code qu'il décrit. Un exemplaire commité pour juger le moteur serait un instantané : il bougerait seulement au réexport, aucune régression ne s'y verrait, un test posé dessus prouverait seulement sa propre immobilité. Les tests de `tests/` jugent ce que le moteur fabrique au moment du test.
- **`tests/dtcg-2025.10/` porte le schéma du module Format DTCG `2025.10`, tel que designtokens.org le sert, avec son empreinte.** Tests : `conformiteDtcg.test.ts` juge chaque feuille des exports du fichier simulé, fixe les chemins exacts du dialecte, ajoute les contrôles que le schéma ne porte pas (marque à la racine, alpha, unité `px`, motif des segments). Le schéma ne se rafraîchit pas : le remplacer suit la décision de viser une autre version du module.
- **`styleDictionary.test.ts` passe le même export sérialisé à Style Dictionary, à la version exacte des `devDependencies` du plugin.** Refuse `[object Object]`, une propriété absente, une référence non résolue, une valeur vide. Borne : ne lit pas la configuration du Playground, dont la preuve est son propre build.
- **Les lois de forme d'un contrat s'appliquent à chaque contrat que le moteur fabrique.** Renvois qui se résolvent ; catalogues sans doublon ni entrée orpheline ; adresses (slotPath de typographie, chemins de peintures, `icons.*.slot`) désignant un calque de l'arbre qui les porte ; aucune valeur neutre écrite ; chaque clé de couleur résolue vers un rôle de la bonne nature ; `inset` réservé aux calques hors du flux ; `textOverflow` publié seulement avec son `lineClamp` ; accord avec le schéma publié ; aller-retour de l'écriture. Autorité : `tests/lois.ts`. Tests : `tests/exportComponent.test.ts`.
- **La vérification est posée sur le chemin d'appel, une fois, pas à chaque scénario.** Un cas ajouté y est soumis sans que personne y pense ; une loi ajoutée à `lois.ts` s'applique du même geste à tous les cas existants.
- **Le même endroit porte la seule question que le schéma ne peut pas trancher seul : accepte-t-il ce que le moteur écrit, et non ce que `types.ts` déclare ?** Un champ requis qu'une élision retire passe le compilateur et casse le consommateur.
- **Chaque export du banc est rejoué avec l'ancien chemin des requêtes extraites, et les deux sorties se comparent objet complet, dans l'ordre.** Contrat hors date, messages, parties, localisations. Le résultat interne de `calculerLAnalyse` se compare ensuite à la sortie publiée, champ à champ : messages, parties, localisations, imbriqués, `props`, `stateModel`, intention, codes de diagnostic, couverture. Le chemin d'avant (modèles de propriétés et d'états) est une copie de test que `remplacerLesRequetesPourLeBanc` installe à la place de la requête. Borne : la case 7.8 du lot « Vitesse de l'analyse » retire l'ancien chemin. Autorité : `tests/aides/parite.ts` `verifierLaPariteDesRequetes`, `verifierLeResultatInterne`. Tests : `plugin-socle/tests/proprietesEtEtats.test.ts`, `plugin-socle/tests/resultat.test.ts`, `tests/budgetEtAnnulation.test.ts`, `plugin-architect/tests/pariteDesRequetesDuMoteur.test.ts`.
- **Les champs qu'un lecteur lit sur un nœud se fixent par un espion.** Un double enveloppe les nœuds de `figmaFaux.node`, note chaque champ et chaque méthode (avec ses arguments) dans l'ordre de première lecture par type de nœud, et le test compare cette liste et la sortie du lecteur. Sert d'oracle quand l'acquisition d'un champ change de lieu. Borne : le jeu observé est un composant à deux variants, pas un corpus. Autorité : `tests/aides/accesDesChamps.ts`. Tests : `projectionDesLecteurs.test.ts` (moteur, budget).
